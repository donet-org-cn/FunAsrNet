# RK3588 更新与原版对比（2026-10-12）

当前版本已在现有 RK3588 部署上替换旧托管服务。模型、音素输入、HTTP/HTTPS 端口及已有证书保持一致。TTS 的同机模型执行对比显示：Huayan 提速 1.74 倍，AISHELL3 提速 1.55 倍；仍比原生 ORT CPU 慢约 2.83 倍和 3.18 倍。

后续已补建固定上游 C++ CPU，对三份 ASR 输入完成新的 52 次正式样本对照，见 [纯 CPU 复测](cpu-native-comparison-20261012.md)。这是直接推理、双方关闭提示词缓存、128 token 的另一批实验，不能与本页旧/新托管 HTTP 的三次样本混算。正式对照之后已更新包含 x64 默认布局修正的程序集；RK3588 上仍使用原 NEON/SDOT 路径，模型、证书和端口不变。

## TTS 的旧部署、新版本和原生对照

环境为 Ubuntu 20.04.5、Linux ARM64、.NET 10.0.10，计算限定到 CPU 4–7 的四个大核，线程数 4。原生对照为 ONNX Runtime 1.23.2 CPU Provider，intra-op=4、inter-op=1、顺序执行、全部图优化。

旧托管基线直接使用替换前正在服务的 `Qcxt.Speech.dll`；将其复制到旧基准程序旁，避免用其他历史构建替代现网基线。新版本使用此次发布的 `FunAsrNet.dll`。二者 SHA-256 与模型、输入散列均记录在 [summary.json](benchmarks/20261012-rk3588-cpu/summary.json)。它与 Windows 优化前基线的程序集不同，因此分别统计各自同机的收益。

下表为预热后的模型 `Run` 中位数 / P95，单位秒：

| 模型 | 替换前旧托管部署 | 当前 C# CPU | 原生 ORT CPU | 提速 | 当前 / ORT |
|---|---:|---:|---:|---:|---:|
| Huayan 0 号 | 2.142 / 2.431 | 1.234 / 1.666 | 0.437 / 0.572 | 1.74 倍 | 2.83 倍 |
| AISHELL3 50 号 | 1.149 / 1.464 | 0.742 / 0.862 | 0.234 / 0.331 | 1.55 倍 | 3.18 倍 |

每个模型按旧托管、新版本、ORT、ORT、新版本、旧托管的顺序运行六个进程块，各先预热一次，再测五次。每种实现各 10 次正式样本；两模型共 60 次正式、12 次预热。只排除显式预热，不删除慢样本；P95 使用最近秩，小样本下等于最大值。

输入与 Windows 测量一致：文本“您好，欢迎致电，请问有什么可以帮您？”，语速 1，两项随机度 0。Huayan 为 69,376 点、22,050 Hz；AISHELL3 为 28,928 点、8,000 Hz。计时只包含模型执行，排除加载、文本前端、文件写入、音频封装和重采样。

每轮在计时区外以温度不高于 60°C 为开始条件，最长等待五分钟。保留系统原有调频策略，未锁频；温度和两个大核簇的频率逐轮记录，因此结果包含动态调频影响。测量期间旧服务保持在线，并检查无其他 ASR/TTS 请求和活动会话。设备已有交换空间占用，本轮 TTS 测量前后的系统换入/换出页计数相同。完整内存与交换计数见记录，不能将此小样本外推为长期并发容量。

## 正确性与部署验证

新版本与原生 ORT 的波形长度相同、全部为有限值；最大绝对误差要求不超过 `0.001`，RMSE 不超过 `0.0001`。

| 模型 | 最大绝对误差 | RMSE | 结果 |
|---|---:|---:|---|
| Huayan | 7.55 × 10⁻⁶ | 4.53 × 10⁻⁷ | 通过 |
| AISHELL3 | 2.99 × 10⁻⁵ | 1.94 × 10⁻⁶ | 通过 |

新、旧托管波形比较也通过。Linux ARM64 与 Windows x64 均通过 685,701 项数值检查，包含多个调用方交替休眠和连续任务的线程组压力测试。早期独立基准暴露了 ARM64 休眠通知的存储/加载竞态，已通过完整屏障修复；固定核心时也为 TTS 调用线程绑定剩余核心，并在结束时恢复。原有服务没有参与该失败基准，失败过程未计入上述正式样本。

多输出 NEON 直接卷积扩展在单独试验中变慢，已撤回，未进入部署及上述正式结果。本次保留已有单输出 NEON 内核与通过验证的缓冲、广播、拷贝和线程调度改动。

## 更新与回滚

保留原有 systemd 服务名称 `rkspeech-dotnet.service`，以独立发布目录和最后生效的 drop-in 切换到新程序。HTTP 18080、HTTPS 18443、模型目录及证书继续沿用；新配置设置 `FUNASRNET_PIN_THREADS=1`。替换前备份旧发布文件、资产、原服务配置和 drop-in；旧目录保留，回滚只需停用新增 drop-in 并重启原配置。

部署前确认语音队列和会话空闲；发布后的 `/health` 已返回 `FunAsrNet`、`ready`、纯 C#、NEON/SDOT 开启、4 线程。HTTP 和 HTTPS 全套接口验收均通过；HTTPS 使用经 SSH 核对的既有证书 SHA-256 指纹。验收包含 WAV 上传、48 kHz 实时转写、不同长度会话、175 个发音人、确定性、参数拒绝和 PCM16/PCMA/PCMU 流式格式。服务替换是一次短暂重启，未改动权重或证书。

## ASR 新旧托管服务对比

替换前、后分别通过同一 `/asr/wav` 接口测量，每个输入各一次预热和三次正式调用，最大输出 512 token。下表为服务返回的 `requestSeconds` 中位数，包含队列调度和完整转写，排除上传、WAV 解码、重采样与响应网络时间。

| 固定输入 | 旧托管服务 | 当前服务 | 本次耗时变化 |
|---|---:|---:|---:|
| 6.000 秒 PCMA | 1.041 秒 | 1.012 秒 | 减少 2.8% |
| 5.616 秒 PCMU | 1.209 秒 | 1.194 秒 | 减少 1.2% |
| 28.000 秒重复拼接 PCMA | 8.237 秒 | 5.169 秒 | 减少 37.2% |

三个输入的新旧输出文本一致。短句差异很小，不能宣称稳定领先；长重复样例本次改善明显，但每边只有三次正式样本，而且按服务替换先后顺序测量，没有 TTS 的交替进程块控制，不能外推为自然长通话或长期尾延迟。逐轮记录和 P95 保留在同目录的 [summary.json](benchmarks/20261012-rk3588-cpu/summary.json)。

Windows 的独立服务验收已覆盖 WAV 上传、48 kHz 实时转写、不同长度会话、175 个发音人、确定性、参数拒绝和三种流式格式。两端原生对照仅针对 TTS 模型执行；本次没有重建已经移除的上游 C++ ASR 程序，不能将 ASR 新旧托管服务比较称为新的 C++ 原版速度对比。历史 C++ 数据仍单独保留。

Windows 的相同输入对比见 [TTS CPU 优化](tts-cpu-optimization.md)，历史原版与计时边界见 [性能比较](performance.md)。
